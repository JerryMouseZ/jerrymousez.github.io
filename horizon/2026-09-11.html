Shopify 将移动应用从 React Native 迁回 Swift 与 Kotlin ⭐️ 8.0/10

Shopify 工程团队发布文章，讲述其移动应用从 React Native 迁回原生 Swift 与 Kotlin 的过程。文章重点介绍了借助 LLM 辅助代码迁移，以及为支持智能体验证而构建的 Playwright 风格“driver”工具。这一案例引发社区对原生与跨平台取舍、以及 LLM 参与大规模重写是否可行的广泛讨论。有评论者认为，该迁移并非只有 LLM 才能完成，并分享了在无 LLM 代码辅助下完成类似迁移的经验。

hackernews · fnthawar2 · 9月10日 14:09 · 社区讨论

「背景」 Shopify 曾在 2020 年为其主力移动应用采用 React Native，主要理由是避免同一功能在 Swift 和 Kotlin 中各写一遍、让开发者跨平台工作，并减少追逐功能对等所花的时间。如今 Shopify 决定放弃这一策略，将移动应用重建为原生的 Swift（iOS）与 Kotlin（Android），其工程博客于 2026 年 9 月 10 日发布了相关说明。

「影响」 Shopify 将把其余应用也陆续迁移到原生开发，这意味着其移动端技术栈将全面转向 Swift 与 Kotlin；同时 Shopify 明确警告，直接让 LLM 对 React Native 代码库做一次性重写并不可行。

「社区讨论」 评论者普遍认可 Shopify 公开迁移细节，并对 LLM 辅助重写持谨慎态度：有人表示不会让 LLM 编写大量核心代码，也有人分享用 Codex 在一夜之间完成约 15-20 个屏幕的跨平台迁移、随后再花数天打磨的经历。多位 iOS 工程师对回归原生表示认同，认为这验证了他们对共享代码库的长期质疑；同时有评论者指出，其参与的中型 React Native 应用原生重写主要工作在 2026 年 1 月前完成且未依赖 LLM 代码辅助，因此“LLM 才使迁移变得可行”的说法并不准确。

Forgejo 16.0.4 修复模板初始化中的严重 RCE 漏洞 ⭐️ 8.0/10

Forgejo 发布了 16.0.4 版本，修复了一个被标记为“严重”的远程代码执行漏洞。该漏洞出现在基于模板仓库生成新仓库的流程中：Forgejo 会克隆模板仓库、删除 .git 目录、对 .forgejo/template 中列出的文件执行变量模板展开，然后初始化新的 git 仓库，而模板展开过程可能干扰 git 仓库初始化，从而被利用。相关修复见 PR 14301，发布说明位于 codeberg.org 的 release-notes-published/16.0.4.md。Gitea 项目领导层成员在讨论中表示 Gitea 不受这两个问题影响。

hackernews · weierstass · 9月10日 15:57 · 社区讨论

「背景」 Forgejo 是一个开源的自托管 Git 代码托管平台，常被用作 Gitea 的社区分支替代方案。该漏洞被追踪为 CVE-2026-89094，影响 16.0.4 之前的版本，攻击者可通过精心构造的模板仓库触发远程代码执行。

「影响」 运行 Forgejo 16.0.3 及更早版本、且允许从模板仓库创建仓库的实例面临远程代码执行风险，应尽快升级到 16.0.4 或 15.0.8。Gitea 维护者表示 Gitea 不受该漏洞影响。

「社区讨论」 社区讨论集中在漏洞细节与安全实践上：有评论者指出发布说明页面因 Codeberg 限流而无法阅读，并转述了修复内容；Gitea 项目领导层成员确认 Gitea 对这两个问题均有防护，同时强调不应因安全事件指责报告者，以免降低漏洞上报意愿。另有评论者将此与 Forgejo 此前禁止 LLM 贡献的决定联系起来，认为攻击者仍会利用 AI 寻找漏洞，这可能使项目处于劣势。

微软将 Rust 列为一级语言 ⭐️ 8.0/10

微软宣布将 Rust 列为一级（tier-1）语言，这一消息来自 RustConf，标志着这家主要操作系统与 C/C++ 工具链厂商对 Rust 的系统编程地位作出正式承诺。社区评论指出，此举意味着所有在 C 和 C++ 语言工具链中扮演角色的主流操作系统厂商，如今都在系统编程语言上实现了选项多元化，尤其面向新项目开发。讨论中提到的关键技术细节是，微软已用 MSVC 后端替换了 LLVM，这被视为本次公告中最实质性的变化，也印证了此前关于 MSVC 集成 Rust 的传闻。此外，RustConf 今年的重点已转向 C++、Python 和 JavaScript 互操作，而非“用 Rust 重写一切”。

hackernews · mmastrac · 9月10日 13:39 · 社区讨论

「背景」 微软内部长期以 C++、C# 和 TypeScript 等语言为主力开发语言，其中 C++ 经过数十年积累仍在系统级开发中占据主导地位。Rust 作为一门强调内存安全与并发安全的系统编程语言，近年来在操作系统与基础设施领域获得越来越多厂商支持。微软此次在 RustConf 2026 上宣布将 Rust 提升为内部开发的 Tier-1 语言，并推出 rustc_codegen_utc，意味着 Rust 在微软内部获得与既有主力语言同等的工具链、质量流程与安全合规支持。

「影响」 对 Windows 上的 Rust 开发者而言，最直接的后果是 Rust 与 C++ 将共享同一套代码生成平台：将 rustc 接入 MSVC 后端后，Rust 可复用微软在 Windows 平台上的既有投入，开箱即用地获得与 C++ 一致的平台兼容性，而无需为每项 Windows 专属能力单独实现一套并行方案。

「社区讨论」 评论者普遍认为这是重大新闻，认为 Rust 已不再是“快速迭代、打破常规”的新兴语言，而是 C++ 和 C# 等成熟语言的严肃竞争者，相比 Zig 和 Odin 等更新的“更好的 C/C++”方案更为成熟。有评论者补充了相关背景：微软曾提出到 2030 年通过自动化工具将 10 亿行代码转换为 Rust 的目标，以及 DARPA 资助多个团队探索自动将 C 代码转换为 Rust 的工作。

trynix.dev 在浏览器中启动任意 Nix 包 ⭐️ 8.0/10

Farid Zakaria 发布了 trynix.dev，它通过 qemu-wasm 在浏览器内运行一个 x86_64 Linux 虚拟机，全部基于 WebAssembly，无需服务器。该虚拟机可以启动过去 13 年间的任意 Nix 包，并且这些包可通过 URL 直接寻址，例如访问 https://trynix.dev/?pkg=python3%403.6.2 并点击“Load”，即可获得一个运行 2017 年 Python 3.6.2 的交互式 shell。Zakaria 称这是他在 Nix 工作上的“magnum opus”。在此之上，他还推出了 trynix-preview：一个 GitHub Action，会在 pull request 上评论一个链接，让审阅者直接在浏览器中启动该 PR 的构建，从而以“启动它”的方式审阅 PR。

rss · Simon Willison · 9月10日 23:44

「背景」 Nix 是一个包管理器与构建系统，其官方软件包集合 nixpkgs 长期保存了历史版本的构建产物，因此可以按版本精确获取过去的软件包。qemu-wasm 则是将 QEMU 模拟器编译为 WebAssembly 的项目，使完整的 x86_64 虚拟机能够在浏览器中运行。trynix 将两者结合，并借助 nixpkgs-multiverse 索引提供对 nixpkgs 历史版本的访问。

「影响」 对 Nix 生态的开发者而言，trynix.dev 让过去 13 年的任意 Nix 包都能通过 URL 在浏览器中直接启动交互式 shell，无需本地安装或服务器；配套的 trynix-preview GitHub Action 会在 PR 上评论一个链接，使评审者能直接在浏览器中启动该 PR 的构建进行验证。

OpenAI 发布 Agents API，开发者热议抽象与锁定 ⭐️ 7.0/10

OpenAI 在其开发者文档中发布了 Agents API 概览指南，将代理（agent）能力作为平台服务提供给开发者。该消息在 Hacker News 上引发讨论，帖子获得 157 分、99 条评论，焦点集中在代理运行框架（harness）的抽象方式、供应商锁定风险以及自托管替代方案上。有评论者指出，文档中提到可以选择自托管沙箱，这被视为降低迁移成本、缓解锁定担忧的关键细节。整体讨论反映出业界对“代理即服务”这一产品形态的抽象设计仍处于探索阶段，尚未形成共识。

hackernews · aquir · 9月10日 19:43 · 社区讨论

「背景」 OpenAI 的 Agents API 将此前用于 Codex 的托管式 agent harness 以 API 形式开放给开发者，提供沙箱、子代理（subagents）和上下文压缩（compaction）等能力，且不额外收费。它与 OpenAI 已有的 Agents SDK 和 Responses API 并列，官方文档建议开发者根据应用场景在 Agents API、Agents SDK 与 Responses API 之间进行选择。在 Agents SDK 中，开发者可以定义 agent 的指令、模型、工具和本地上下文。

「影响」 对构建智能体系统的开发者而言，Agents API 将 Codex 的编排、长会话与上下文管理能力封装为托管服务，并允许在 OpenAI 托管沙箱、自有基础设施或合作方沙箱中运行智能体计算，从而降低了自建 harness 的门槛，也为跨供应商迁移留出空间。

「社区讨论」 评论者普遍认为代理产品的正确抽象尚未定型：有人指出自建 harness 是巨大的工程投入，而开源库仍与环境耦合，状态持久化位置（如无文件系统的 Cloudflare Worker）是核心难题。多位开发者对供应商锁定表示警惕，有人强调可通过自建 QEMU 虚拟机运行 Codex 并用远程控制实现个人助理，从而避免被锁定；也有人批评应优先提供所付费的推理 token。另有观点认为普通 LLM 端点与代理/harness 的界限将日益模糊，最终“给模型一台计算机”即可。

布朗大学报告：硅谷如何重塑军工复合体 ⭐️ 7.0/10

布朗大学“战争成本”项目发布报告，分析大型科技公司与硅谷在军工复合体中日益扩大的角色，并追溯了科技行业与国防部门长期的历史联系。报告举例指出，旧金山小公司 Keyhole 在 2003 年获得中情局支持的 In-Q-Tel 种子投资，其三维地球建模软件在两周内即被军方和情报机构用于支持伊拉克战争，次年 Google 收购 Keyhole 并将其更名为 Google Earth。该报告在 Hacker News 上引发 315 条评论的广泛讨论，争论焦点包括科技行业与国防的历史渊源、企业是否应承接本国国防合同，以及科技工作者在其中的责任。

hackernews · paimapi · 9月10日 15:47 · 社区讨论

「背景」 “军工复合体”（military-industrial complex）一词源自美国总统艾森豪威尔 1961 年的告别演说，用以警示国防工业与军方之间日益紧密的利益关系。硅谷与国防体系的联系并非始于近年：从 Fairchild 半导体时代起，军方就是芯片产业的主要客户，而 Google Earth 的前身 Keyhole 曾于 2003 年获得中情局支持的 In-Q-Tel 种子投资。据《纽约时报》2025 年 8 月的报道，Google、OpenAI、Meta 等公司及风险投资机构正从过去回避涉足战争转向积极拥抱军工业务，这一转变构成了当前讨论的直接背景。

「影响」 该报告指出，受益于机密国防合同的硅谷初创企业、大型科技公司和风险投资将催生昂贵、低效、不可预测且不安全的高科技国防产品，最终由美国纳税人买单。
