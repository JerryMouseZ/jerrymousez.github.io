Quad9 因法院封锁令与藐视罚款退出法国 ⭐️ 8.0/10

公共 DNS 解析器 Quad9 宣布将退出法国市场。此前法国法院认定其未遵守网站封锁命令，并对其处以藐视法庭罚款。Quad9 首席技术官在讨论中表示，公司可能在 11 月 24 日之后使用 geoIP 过滤阻止法国用户访问其服务，同时承认 geoIP 封锁无法精确地只对特定域名停止解析，这一矛盾正是争议焦点。该决定属于已宣布的退出计划，具体执行方式尚未最终确定。

hackernews · farrokhi · 10月22日 14:32 · 社区讨论

「背景」 Quad9 此前已在法国面临由广播机构 Canal+ 发起的网站屏蔽禁令，并被要求屏蔽 58 个域名，否则将面临 58 万欧元罚款。据社区评论引述，Quad9 曾就相关合规问题与 Sony Music 产生争议，后者通过 VPN 从德国访问被屏蔽内容，法院据此认定 Quad9 未合规并处以藐视法庭罚款。

「对法国用户的影响」 Quad9 的 CTO 表示，公司很可能在 11 月 24 日之后通过 geoIP 过滤阻止法国用户访问其服务，这意味着法国境内的用户将无法再使用 Quad9 进行 DNS 解析，需要改用其他解析器。这一退出并非孤例：Cisco 的 OpenDNS 自 2024 年 6 月 28 日起已因法国体育法典相关法院命令对法国用户不可用，而 2026 年 4 月的报道显示 Google、Cloudflare 和 Cisco 在法国针对盗版网站的 DNS 屏蔽上诉中败诉，第三方解析器可被要求执行屏蔽。

「社区讨论」 有评论指出，原告索尼音乐曾用 VPN 从德国绕过 geoIP 封锁访问被封锁内容，法院据此认定 Quad9 未合规并处以罚款，评论者认为这让服务商陷入两难。另有评论提到，Canal+ 此前已针对 Google、Cloudflare 和 Cisco 的 DNS 解析器申请封锁令，Cisco 约两年前退出法国市场，Quad9 的举动与之类似。也有评论质疑惩罚 DNS 解析器是否合理，并将其比作因电话簿收录罪犯号码而惩罚电话簿公司。

甲骨文发布 Java SE JSSE 高危漏洞警报 ⭐️ 8.0/10

甲骨文发布安全警报，披露 Java SE 的 JSSE 组件存在编号 CVE-2026-91403 的漏洞，CVSS 评分 9.1，攻击者无需身份验证即可通过网络远程利用，可能严重破坏数据的机密性与完整性。受影响版本包括 Java SE 8u511、11.0.33、17.0.21、21.0.13、25.0.5、27.0.1 以及多个 GraalVM 版本。甲骨文表示已同步推出修复补丁，并建议用户升级至受支持版本。警报未披露漏洞的技术根因或利用细节。

telegram · zaihuapd · 10月22日 12:30

「影响与应对」 使用上述 Java SE 或 GraalVM 版本、且对外暴露 JSSE 相关网络服务的组织应优先安排升级到已修复的受支持版本，因为该漏洞可被未认证的远程攻击者利用。由于警报未说明具体触发条件，在补丁部署前难以评估哪些部署场景风险最高。

333 个 Tor 出口节点被植入 Ebury 后门后下线 ⭐️ 8.0/10

一名 Tor 运营者用脚本扫描了约 3000 个出口中继，发现其中 333 个（约 10%）被植入 Ebury 后门。这些节点会把 22 端口的 SSH 连接劫持到 12 台拦截服务器以窃取凭据，攻击者还在今年 8 月入侵了这些服务器，并屏蔽部分端口以专门收集未加密的邮件流量。相关节点于 10 月 4 日被标记为 BadExit，次日全部下线；入侵途径目前尚无定论。

telegram · zaihuapd · 10月22日 14:52

「背景」 Ebury 是一种针对 Linux 服务器的 OpenSSH 后门与凭据窃取工具，通常通过替换 ssh、sshd 等二进制文件或修改 OpenSSH 使用的共享库（如 libkeyutils）植入，攻击者需要先取得 root 级权限。它被用于维持访问、窃取认证信息并重定向流量，这与本次出口中继劫持 22 端口 SSH 连接的手法一致。

「影响与应对」 对依赖 Tor 出口节点保护流量的用户而言，约 10% 的出口中继曾可被用于劫持 22 端口 SSH 连接并窃取凭据，经这些节点传输的未加密邮件流量也可能已被收集。由于入侵途径尚未确定，仅更换凭据不足以排除风险；使用 SSH 或明文协议的用户应优先改用密钥认证和端到端加密，并核查相关时段是否有异常登录。

NVIDIA 开源 OpenShell：为自主 AI 智能体提供受限运行时 ⭐️ 7.0/10

NVIDIA 在 GitHub 上发布了开源项目 OpenShell，定位为运行成批自主 AI 智能体的运行时，通过限制智能体对文件、密钥和网络的访问来降低风险。项目宣称的目标是让智能体在能读文件、装软件包、调用 API 和使用凭据的同时，不获得对用户数据、密钥或网络的完全访问权。目前公开信息仅有仓库标题和简介，尚无具体版本号、支持的平台、隔离机制细节或独立测试结果，因此其安全边界仍属厂商描述而非已验证能力。

hackernews · niemandhier · 10月22日 17:44 · 社区讨论

「背景」 自主 AI 代理通常需要读取文件、安装软件包、调用 API 并使用凭据，这使其具备实际能力的同时也带来数据、密钥和网络访问风险。OpenShell 的定位是在隔离沙箱中运行代理，并按声明的策略约束其文件访问、系统调用、网络连接、凭据和模型调用。

「对使用者的影响」 OpenShell 面向需要让智能体读取文件、安装软件包、调用 API 并使用凭据，同时又要限制其对数据、密钥和网络访问的场景。由于来源未提供具体隔离机制、版本或兼容性细节，目前无法确认其防护强度；评估时应分别核实文件、密钥与网络三类访问控制的实际实现，而非仅依赖项目描述。

「社区讨论」 评论者普遍认可智能体需要沙箱，但质疑“既给足权限又保证安全”的说法：smallnix 认为权限越大能力越强，二者无法兼得，简介读起来像夸大。fennecbutt 提到用 iron proxy 做域名级网络限制和凭据替换，但指出真正的难点是防止代码库等数据外泄，仅靠限制可信域名并不够。另有评论者建议复用 Warpgate、Teleport 等现有访问网关，而不是另造一套。

eMudhra 宣布退出全球 SSL/TLS 证书业务 ⭐️ 7.0/10

eMudhra 发布新闻稿，宣布将退出全球 SSL/TLS 证书业务。新闻稿称，此次决定与一起事件引发的关注有关，并强调其全球 SSL/TLS 基础设施与其他业务分开运行。新闻稿未在可见内容中说明事件的具体技术原因或责任认定，因此该退出目前是公司公告层面的计划，而非已完成的业务关停。

hackernews · bo0tzz · 10月22日 13:33 · 社区讨论

vLLM 为 MiniMax-M3.1-Flash 提供首日支持 ⭐️ 8.0/10

rss · vLLM Blog · 10月23日 00:00

「背景」 MiniMax-M3.1-Flash 是 MiniMax-M3 家族的新模型，原生采用 NVFP4 KV 缓存与 NVFP4 量化的 MoE 权重，并配有 DSpark 草稿模型做投机解码。长上下文解码受显存带宽限制，而该模型用块稀疏注意力（MSA）把每个查询的注意力范围限制在最多 2048 个键，使每步 HBM 流量降到稠密注意力的约 12.5%。vLLM 团队要解决的是：如何在 NVIDIA Blackwell、Rubin 和 AMD MI350 上让这套低精度、稀疏的推理路径真正跑得快。

「方案」 作者的核心思路是围绕 NVFP4 数据格式和 MSA 的访存模式做内核级融合，而不是简单换 dtype。在 Blackwell 上，由于查询是 FP8、KV 是 NVFP4，无法直接用 NVFP4 张量核心，内核改用 CUDA 13.4 新增的 QMUL4 指令在核内把 NVFP4 反量化为 FP8，索引器 QK 解码最高快 1.7 倍、稀疏注意力解码快 1.3 倍。NVFP4 MegaMoE 融合 MXFP8 共享专家，并在 FC1 尾声把累加器载入寄存器后立即释放 TMEM，使 prefill 内核延迟降 20%、吞吐升 7%。索引器解码上下文并行（DCP）按上下文切分工作，各 GPU 只算四分之一页面再经 NVLink 交换候选，512K 上下文下每稀疏层快 3.3 倍且选择仍精确。QKV GEMM 与 norm、RoPE、KV 写入融合成单个内核，QKV 张量不再落 HBM，prefill 快 1.1–1.6 倍、TP4 下 P50 TTFT 降约 19%。Rubin 上则把 NVFP4 直接转 FP16 做索引器打分，减少约三分之一反量化指令并避免 E4M3 重舍入，同时利用更大共享内存和 212 个 SM 做负载均衡。AMD 侧因 CDNA4 无原生 NVFP4 反量化指令，改用 2KB LDS 查表加字节置换完成转换，稀疏解码注意力快 2.5 倍；DCP 还顺带填满 MFMA 列，索引器每层快 2.8 倍；单内核 mono decode 把约 1170 次启动合并为一次，低并发解码快 2.3 倍。作者也坦承权衡：Rubin 仍有 NVFP4 转 FP8 的开销，AMD 低并发受启动开销约束。基准显示 GB300 上每用户最高 418.9 tok/s，Rubin 上 724.9 tok/s、每 GPU 191.5K tok/s，MI355X 上每美元 TCO 达 133.3M token；RL 方面 200 步 GRPO 把 AIME-2024 从 36.3% 提到 67.5%。

「启示」 作者想说明的是，低精度格式的收益不只来自位宽减半，更取决于是否围绕具体硬件补齐反量化、融合与并行策略；这些内核融合和访存推理对其他推理优化同样有借鉴意义，但具体数字高度依赖该模型与硬件组合。

软件慢源于设计而非语言速度 ⭐️ 7.0/10

rss · Sean Goedecke · 10月23日 00:00

「背景」 面对“用 AI 把程序改写成 C 或 Rust 就能大幅提速”的流行说法，作者认为这通常不成立：尽管 C 可能比 Python 快数十倍，但多数真实程序的性能瓶颈并不在语言本身。

「方案」 作者的核心论据是 I/O 主导性能。以一个简单 CRUD 网站为例，若一半请求时间花在数据库查询上，改用 C 重写也只能优化另一半，按 Amdahl 定律最多约 2 倍、实际可能只有 1.5 倍，远达不到数量级提升；等待第三方 API、磁盘或网络的程序同样如此。对于确实 CPU 密集的工作，慢语言往往已通过库把计算交给快语言：Markdown 渲染调用 cmark-gfm，Python 的机器学习依赖底层 C 或 GPU 代码，因此重写外层语言收益有限。作者引用 Bryan Cantrill 2018 年的经历：他放弃把精心优化的 C 程序逐行移植到 Rust，改用朴素写法，结果反而快 30%，原因之一是 Rust 内部采用更缓存友好的 B 树而非二叉搜索树，说明即便在 CPU 密集场景，设计也压过语言速度。作者自己取得的大幅提速几乎都来自“让程序少做事”：缓存慢操作、异步化、并行化、合并 SQL 查询以消除 N+1、替换慢查询、跳过不必要的操作，这些都与语言快慢无关，而高层语言反而更容易看清问题。他也承认存在例外，如有人用汇编重写 tiktoken 获得提升，但指出这更多源于避开正则依赖的设计改变，且分词只占推理时间的一小部分。

「启示」 作者主张，与其让 AI 代理一上来就把程序重写成 Rust、C 或汇编，不如先做性能剖析、定位热点、重新设计程序以减少工作量；只有在极少数真正 CPU 密集且无法重构的热点上，才值得局部换用更快的语言。
