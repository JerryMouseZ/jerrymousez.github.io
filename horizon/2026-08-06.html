Deno 发布 Celld：自托管分布式 Durable Objects ⭐️ 8.0/10

Deno 发布了 Celld，一个自托管、分布式的 Durable Objects 实现，为 Cloudflare 的同类服务提供了可移植的替代方案。Celld 中的每个对象都由独立的 SQLite 数据库支持，并通过名称寻址，同时复制到用户拥有的 S3 兼容存储桶中。该项目旨在满足开发者对超越单一云提供商的可移植性需求，并已在 Hacker News 上引发社区关注。Celld 的架构强调简单性和强大功能，使得分布式状态管理更加易于访问。该项目的发布标志着 Durable Objects 抽象在开源生态中的进一步发展。

hackernews · calvinfo · 8月5日 16:50 · 社区讨论

「背景」 Durable Objects 是 Cloudflare Workers 提供的一种抽象，允许开发者在边缘运行有状态的服务，每个对象拥有独立的状态和存储。Celld 是 Deno 推出的开源守护进程，能够在用户自己的机器上运行 Cloudflare Workers 和 Durable Objects。每个对象对应一个独立的 SQLite 数据库，通过名称寻址，并复制到用户拥有的 S3 兼容存储桶中；节点之间仅通过该存储桶协调，无需控制平面或共识协议。

「影响」 对于寻求自托管或跨云部署 Durable Objects 的开发者，Celld 提供了 Cloudflare 之外的可行选择，可能降低对单一供应商的依赖。其基于 SQLite 和 S3 的复制机制，为需要分布式状态管理的应用提供了简单而强大的基础。

「社区讨论」 社区对 Celld 的发布反应积极，认为自托管分布式 Durable Objects 是去中心化节点维护可靠状态的重大进步。有用户询问 Celld 与 Cloudflare 开源版本 workerd 的区别，也有用户分享了在 Cloudflare 上使用 Durable Objects 的成功经验，并对更多非 Cloudflare 选项表示期待。此外，项目禁用 Pull Request 的决定也引发了关于维护者时间和代码贡献流程的讨论。

Webhook 状态同步的困境与订阅式替代方案 ⭐️ 8.0/10

一篇技术深度文章剖析了使用 Webhook 进行状态同步的诸多问题，包括签名验证、去重、缓冲、引导和定时任务等，并提出了一个名为 SCROLL 的订阅式替代方案。该方案与作者 toomim 正在提交至 IETF 127 的“Braid-HTTP Subscriptions”草案高度相似，核心是通过 GET 请求加 Prefer: stream 头来建立持续订阅。文章指出，Webhook 在状态同步场景下存在不可靠性，例如 QuickBooks API 有时返回错误但实际已创建实体，导致开发者必须手动核对。社区讨论中，有观点认为持续连接可能效率低下，并建议保留 Webhook 作为“提示”信号，结合低频率轮询来平衡实时性与资源消耗。

hackernews · weli · 8月5日 15:22 · 社区讨论

「背景」 Webhook 是一种常见的 API 回调机制，用于在事件发生时向客户端发送通知，但它在状态同步场景中存在可靠性问题，如消息丢失、重复和顺序混乱。IETF 正在探索更标准化的同步协议，例如 Braid-HTTP 草案，该草案提出通过 HTTP 扩展实现实时同步。本文提出的 SCROLL 方案与 Braid-HTTP 订阅机制类似，均通过 GET 请求加自定义头部（如 Prefer: stream）来建立订阅流。

「影响」 对于依赖 Webhook 进行状态同步的开发者，该文章及其讨论提供了替代方案和最佳实践，可能推动采用订阅式协议或混合轮询策略，以提高同步的可靠性和效率。

「社区讨论」 社区评论中，toomim 指出 SCROLL 草案与他的 IETF 草案相似，alt227 分享了 QuickBooks API 的不可靠实例，bytesandbots 担忧持续连接的开销，tlonny 则建议将 Webhook 作为“提示”结合轮询，体现了对方案可行性和效率的多元观点。

豆包上线原生音视频全双工模型 SeedRealtime ⭐️ 8.0/10

字节跳动于 8 月 5 日发布原生音视频全双工大模型 SeedRealtime，该模型采用统一架构融合音频、视频与文本，支持在连续多模态信息流上实时交互，具备音视频联合理解、主动环境感知与流畅对话节奏三项核心能力。端到端人工评测显示，其音视频对话节奏问题较级联模型减少一半，&#x27;话未说完被抢断&#x27;等卡壳现象显著减少。目前该模型已在豆包 App 全量上线。不同于传统级联系统依赖 ASR、VLM、TTS 多模块串联造成的延迟与信息损耗，SeedRealtime 将感知、理解、决策与表达纳入同一端到端模型同步进行，无需外置 VAD 判断轮次，可实现&#x27;边看、边听、边说&#x27;的全双工自然交互。

telegram · zaihuapd · 8月5日 04:42

「背景」 传统的实时语音交互系统通常采用级联架构，即依次串联自动语音识别（ASR）、视觉语言模型（VLM）和文本转语音（TTS）等独立模块，每个模块处理一个环节，导致延迟累积和信息损耗。SeedRealtime 是字节跳动推出的原生音视频全双工大模型，采用统一的端到端架构，将感知、理解、决策与表达整合在同一模型中，无需外置的语音活动检测（VAD）来判断对话轮次，从而支持“边看、边听、边说”的实时交互。

「影响」 对于豆包 App 的用户，SeedRealtime 的上线意味着实时语音视频对话的流畅度和自然度将显著提升，减少了因模块串联导致的延迟和打断问题。对于 AI 行业，这一原生全双工架构可能推动实时多模态交互技术的范式转变，促使其他厂商跟进类似端到端方案。

Monodratic：基于学习乘积哈希路由的稀疏因果注意力 ⭐️ 7.0/10

独立研究者分享了 Monodratic，一种采用学习乘积哈希路由的稀疏因果注意力架构。该机制在 RoPE 后将源块分配到有界因果发布列表，查询通过乘积地址探测、重排序并选择固定数量的远程源块，加上保证的局部块，然后仅对这些 token 执行精确因果 softmax。在关联回忆任务中，学习路由（从 5 个合格块中选择 2 个远程块）在三个随机种子下达到 763/768 正确（平均 99.35%，最低 98.05%），而等宽未训练路由为 425/768，仅局部注意力为 151/768。强制目标块并保持相同最大 R2 注意力预算可恢复全部五个剩余错误，达到 768/768。稀疏选择集注意力与独立密集选择掩码 oracle 的最大绝对误差为 1.43e-6，打包 CPU 路由实现在 4,096 到 32,768 token 范围内拟合时间指数为 0.993，所有学习路由和扩展运行均无发布溢出。局限包括合成实验、可移植 PyTorch 实现而非融合内核，以及未声称自然语言质量、渐近线性构建或部署速度。

「背景」 标准因果注意力对所有先前 token 计算注意力，导致序列长度二次方的时间和内存成本。稀疏注意力通过仅关注部分 token 来缓解这一问题，但如何选择这些 token 是关键挑战；学习路由方法旨在从数据中学习选择策略，而非使用固定模式。Monodratic 采用乘积哈希将查询映射到候选源块，结合局部块保证，在保持精确 softmax 的同时实现稀疏化。
