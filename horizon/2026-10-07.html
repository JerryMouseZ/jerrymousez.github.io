OpenAI 发布数学预印本，声称证明 Barnette 猜想 ⭐️ 9.0/10

OpenAI 在 GitHub 上发布了数学预印本集合（github.com/openai/math/tree/main/preprints），其中包含对若干长期未解问题的证明，例如 Barnette 猜想，以及一个自 1979 年 Garey 和 Johnson 著作以来悬而未决的三机单位作业调度多项式时间算法。这些材料以预印本形式公开，尚未经过同行评审，来源内容本身主要是链接，未提供验证状态。

hackernews · OfficialTurkey · 10月6日 22:17 · 社区讨论

「背景」 Barnette 猜想是图论中长期未解的公开问题。据外部资料，2026 年 8 月一项 AI 研究项目曾尝试攻克该猜想，但当时该猜想仍属未解，其符号论证未经合格人类评审认证，计算性结论仅适用于明确列出的输入与搜索边界，内部 AI 评审和独立验证程序均不等同于同行评审（tool-2-1）。OpenAI 此次发布的预印本声称给出了该猜想的证明，并同时给出自 1979 年 Garey 与 Johnson 著作以来一直未解的三机器单位作业调度多项式时间算法。

「影响」 这些预印本目前只是未经同行评审的声明，因此数学界和理论计算机科学界的研究者需要独立验证证明，而不能直接将其视为已确立的结果。对调度理论而言，若三机单位作业调度的多项式时间算法成立，将解决自 1979 年 Garey 和 Johnson 著作以来悬而未决的问题，并可能影响依赖该问题复杂性假设的后续工作。

「社区讨论」 一位自称研究 Barnette 猜想长达 24 年的评论者表示，看到该问题被列为已证明（问题 180）后不知该如何看待，并提到自己去年夏天曾短暂以为解决了它。另一位从事理论计算机科学与调度的评论者认为，三机调度结果的重要性低于 UGC，但指出该问题自 1979 年以来一直开放；还有评论者称自己曾用前沿模型尝试 Barnette 猜想但失败，并认为公开的证明初看可行。

Mistral 发布 Large 4：欧洲自建 3800 块 GB 显卡从头训练 ⭐️ 8.0/10

Mistral 发布旗舰模型 Mistral Large 4（ML4），官方称其在欧洲自有数据中心使用约 3800 块 NVIDIA Grace Blackwell GPU 从头训练，并宣称在视觉与网络安全基准上表现强劲。据社区评论转述，Mistral 报告 CyberGym-E2E 得分 82%，视觉定位在 Dense 200 上为 42%（对比 GPT-6 Astra 的 41%）。该模型仅提供 reasoning "none" 与 "high" 两档设置，且据用户实测两档差异不明显。上述基准与训练细节均来自厂商声明，尚无独立验证。

hackernews · Philpax · 10月6日 13:15 · 社区讨论

「背景」 Mistral Large 4 是 Mistral 的旗舰级开源权重多模态模型，采用细粒度混合专家（MoE）架构，总参数约 1.05T、激活参数 52B，并配有 1.6B 视觉编码器，上下文窗口为 512k token。据发布信息，该模型于 2026 年 10 月 6 日发布，距 Mistral Medium 3.5 约 160 天。

「影响」 Mistral Large 4 目前处于公开预览阶段，训练完全在欧洲自有数据中心完成，这对需要欧盟境内训练与推理的数据主权敏感型组织具有直接意义。社区评论指出其在网络安全基准上表现突出（Mistral 报告 CyberGym-E2E 达 82%），可作为 GLM-5.3 等模型的替代选项；但推理模式仅支持 none 或 high，且实测两者差异有限，采用前需针对具体任务验证。

「社区讨论」 simonw 实测发现 reasoning "none" 与 "high" 差别很小，high 档反而输出更少 token，但认为其生成的 SVG 图（如自行车、鹈鹕）是所见 Mistral 模型中最好的。abixb 则提出疑问：若约 1T 参数模型仅用约 4000 块 GB GPU 从头训练就能接近 Kimi K3 水平，这对其他实验室意味着什么。michaelkdev 认为即便不是最强模型，在欧洲训练与推理对欧盟技术主权仍有价值。

Google 发布 Apache 2.0 许可的 EmbeddingGemma 2 多模态嵌入模型 ⭐️ 8.0/10

Google 发布了 EmbeddingGemma 2，一款以 Apache 2.0 许可开放权重的轻量级多模态嵌入模型，可将文本、图像、视频帧和音频映射到统一向量空间，主打本地隐私检索。据社区讨论，文本专用版本为 270M 参数，文本加视觉版本合计 440M 参数；另有中文来源称模型总参数为 740M，两者口径不一致。配套的 Google AI Edge Gallery 新增即时媒体搜索和视频时刻查找演示，Mac 版 Foresight 提供本地会议助手，模型预计未来数周通过 ML Kit 向 Android 开放。

hackernews · ilreb · 10月6日 16:03 · 社区讨论

「背景」 EmbeddingGemma 2 是 Google DeepMind 于 2026 年 10 月 6 日发布的开放权重多模态嵌入模型，采用 Apache 2.0 许可，参数规模为 740M，基于 Gemma 4 架构，面向端侧推理。嵌入模型是检索增强生成（RAG）和智能体系统的基础组件，此前社区一直缺少一个许可宽松、中等规模且支持多模态的开放选项。

「影响」 对需要在本地或私有环境构建 RAG 与检索管线的开发者而言，Apache 2.0 许可意味着可以自行托管并长期保存已生成的嵌入向量，而不必担心托管方停用某个专有模型后历史向量失效。若计划在 Android 端部署，需注意 ML Kit 支持尚未落地，目前仅宣布将在未来数周开放。

「社区讨论」 Hacker News 评论者 simonw 认为嵌入模型不适合采用闭源、仅托管的形式，因为应用往往要计算并存储成千上万条向量，供应商一旦停用旧模型就会带来迁移问题；minimaxir 则表示此前缺少中等规模的优质嵌入模型，并称 270M 文本版和 440M 文本加视觉版尺寸合理。anyg 指出 Google 把多模态输入决策相关 API 放在第三个示例中，认为若将其作为主打可能获得更多关注。

合成非语言先验训练模型实现上下文语言学习 ⭐️ 8.0/10

一篇论文提出了一种“语言先验”：每条训练序列都来自随机采样的循环因果模型，因此每个序列都是一种新的合成“语言”。一个仅在这些合成序列上训练的 3 亿参数字节级 Transformer，在权重冻结的情况下，能够对真实语言进行上下文预测。在维基百科文本上，其下一字节预测随阅读量增加而改善，在英语、中文、印地语、阿拉伯语、日语和韩语六种语言中，从每字节 8 比特降至读取一百万字节后的 0.9–2.4 比特。该模型还能在上下文中学习计数、比较数字、近似加法以及预测素数或 Kolakoski 序列等确定性序列。作者指出，该模型在文本上的表现仍远逊于在数万亿 token 上训练的经典语言模型，因为它在测试时最多只看到一百万字节的语言数据。

reddit · r/MachineLearning · /u/cbl007 · 10月6日 10:50

「背景」 先验拟合网络（prior-fitted network）的思路源自 TabPFN：模型在大量合成数据上预训练，从而能在推理时仅凭上下文学习真实表格数据，无需更新权重。该论文将这一思路从表格数据扩展到结构化序列，用随机采样的循环因果模型生成合成“语言”作为训练先验，再测试模型能否在冻结权重下于上下文中学习真实自然语言。

「影响」 这项工作将 prior-fitted networks（TabPFN 背后的思路）从表格数据扩展到结构化序列和自然语言，表明上下文学习语言的能力可以来自合成的非语言先验。对于研究上下文学习和合成数据训练的研究者，该模型、代码和权重已公开，可供复现和进一步实验。

OpenAI Decisions API 进入公开测试 ⭐️ 7.0/10

OpenAI 的 Decisions API 已进入公开测试阶段，开发者可通过 /v1/decisions 端点调用，请求体包含 model 与 input 字段。社区评论显示该接口底层使用 gpt-6-luna 模型，支持 100 万 token 输入窗口和图像等多模态输入。有开发者实测端到端延迟约 160–175 毫秒，最差 5% 为 285 毫秒，最慢一次为 743 毫秒。目前尚无官方定价与正式可用性细节，相关性能数据来自社区个人测试而非独立验证。

hackernews · chiefstorm · 10月6日 20:57 · 社区讨论

「背景」 OpenAI 此前通过 Responses API 提供 GPT-6 Luna 的文本与图像输入能力，而 Decisions API 是新增的独立端点（POST /v1/decisions），让模型对输入直接返回数字或标签而非生成文本，官方称其决策速度最高可达 GPT-6 Luna 的 10 倍。该端点目前仅由 GPT-6 Luna 驱动，处于公开测试阶段。

「影响」 对开发者而言，OpenAI 的 Decisions API 进入公开测试意味着可以直接调用一个决策专用端点，但社区实测显示其延迟在 160–175 毫秒之间（最差 5% 为 285 毫秒），且目前缺少缓存机制，长系统提示或追问场景需要自行承担重复输入成本。社区成员 Topfi 用不到 600 次调用在 OpenRouter 上对比了 Jev 与 Mercury Decide，说明选型时已有可参考的替代方案；而 Jev 的定价为每百万输入 token 0.042 美元、输出 token 免费，若成本是主要约束，开发者可能需要在 OpenAI 的决策 API 与这类低价专用模型之间做权衡。

「社区讨论」 开发者 Topfi 表示已在 OpenRouter 上用不到 600 次调用对 Decisions API、Jev 和 Mercury Decide 做了初步评测，场景包括 UI 组件选择、聊天图表和标签选择。TSiege 认为 Jev 的出现及其开源版本涌入 Hugging Face，说明决策类模型正在走向商品化，大厂可能为留住客户而压低价格。AM1010101 则指出该 API 未提供缓存机制，长系统提示或追问场景下缓存会更有价值。

AnyPS5 项目声称无需模拟即可在 PC 运行 PS5 二进制 ⭐️ 7.0/10

GitHub 项目 AnyPS5 声称能在 PC 上运行 PS5 二进制文件，方式是将 87% 的 PS5 系统库映射到 PC 环境，而非通过模拟器执行。该项目由 boykopovar 发布，在 Hacker News 上引发讨论，但仓库未提供独立验证、基准测试数据或法律与技术分析，因此 87% 这一比例和“无需模拟”的说法目前仍属项目方主张，而非已确认的能力。

hackernews · Fe2O3 · 10月6日 23:28 · 社区讨论

「背景」 传统上在 PC 上运行主机游戏依赖模拟器，例如 Yuzu 和 Ryujinx 通过软件模拟 Switch 硬件来执行游戏。AnyPS5 走的是另一条路线：据其 GitHub 页面描述，它用重链接器（relinker）把 PS5 可执行文件转换为目标系统的原生格式，并实现主机的系统 PRX 库以完成动态链接，再通过 Vulkan 重新编译主机着色器，从而在 Linux 和 Windows 上运行，而非模拟 PS5 硬件。

「影响」 该项目目前仅有 GitHub 仓库和 87% 的库映射声明，没有独立验证、基准测试或法律分析，因此对普通用户的实际可用性尚不明确。社区评论者提醒，类似项目可能面临法律下架风险，此前任天堂曾让 Switch 模拟器 Ryujinx 的下载页面清空，Yuzu 也遭遇过类似情况，因此建议对仓库做本地镜像备份。

「社区讨论」 有评论者认为，此类逆向工程会促使索尼、任天堂和微软更倾向云游戏，从而限制本地运行的可能性；也有人建议对这类项目做本地 git 克隆备份，因为类似 Yuzu 和 Ryujinx 的项目曾因法律压力被下架。另有评论质疑，如果软件能在发售首日被提取运行，还有谁会付费购买，并担忧软件产业比重大的国家将受到冲击。

OpenTPU 是一个开源 AI 推理加速器项目，作者 fsbonetto 称其开发沿用了此前用 AI 设计 RISC-V CPU 内核的方法，并通过递归自改进循环把性能从最初每秒仅几个 token 提升到在较小模型上 80+ token/秒。作者表示它可运行 Qwen 3.5、Gemma 4 等多数现代模型。上述性能与兼容性均为作者自述，仓库本身未在本次信息中经过独立验证。

hackernews · fsbonetto · 10月6日 16:23 · 社区讨论

「背景」 OpenTPU 是一个开源 AI 推理加速器项目，其仓库包含 RTL、ISA、模拟器、编译器和性能分析器，并声称可在 Kintex-7 PCIe 卡上运行 Qwen3、LFM2.5 和 Qwen3.5 等模型。项目作者 fsbonetto 在评论中表示，此前曾用 AI 开发 RISC-V CPU 核，随后将同样方法用于 OpenTPU，并通过递归自我改进循环把吞吐从每秒几个 token 提升到小模型上的 80+ tok/sec。这些性能与开发方式目前主要来自作者自述，尚未见到独立验证。

「影响」 该项目目前仅有作者自述的性能数据，尚无独立验证，因此开发者若考虑采用，应先自行复现 80+ tok/sec 的推理结果并确认其对 Qwen 3.5、Gemma 4 等模型的实际支持范围。作者称同一套 AI 辅助方法此前也用于开发 RISC-V CPU 核心，但该说法同样未在本次材料中得到第三方确认。

科技博客

如何阅读代码：非线性多轮扫描法 ⭐️ 7.0/10

rss · Sean Goedecke · 10月7日 00:00

「背景」 多数人习惯像读书一样从头到尾顺序阅读代码，但代码的执行顺序由计算机决定，且工程师日常面对的多是 diff 而非全新程序，其结构复杂度也远超自然文本。作者认为，大型程序复杂到单个人无法完全理解，顺序阅读往往让人迷失执行流、忽略未改动部分，最终只能靠猜。

「方案」 作者借鉴阅读数学论文的“二分扫描”技巧，主张对代码进行多轮、非线性的聚焦阅读。他先选一条重要路径（如 diff 引入功能的 happy path），追踪函数间的调用关系以把握整体流程，再细看这些函数具体做什么；随后沿不同线索做多轮扫描，用 ctrl+f 或 ctrl+click 在调用点间跳转，把当前不关注的部分一律当作黑盒。只有在确信理解 diff 后，他才从头到尾精读一遍，目的不是学结构，而是捕捉此前遗漏的怪异之处，发现异常再回到扫描。作者强调每轮都很快，因为不必逐行苦思。对于 LLM 能否代读代码，他认为不能：AI 生成的代码常出现“对齐”问题而非 bug，例如一个只需透传一个值的小改动，因 agent 发现一个设计上无害的竞态条件，膨胀成三千行的复杂修复。即便 LLM 不犯错，其技术价值观也未必与你或公司一致，因此仍需仔细阅读代码本身及 LLM 的输出。

「启示」 作者的核心论点是：代码不是散文，应按结构而非顺序阅读，通过多轮聚焦扫描先建骨架再补细节，最后才做端到端精读。LLM 可以辅助阅读，但无法替代工程师亲自理解代码，因为真正的风险往往不是错误，而是技术价值观的错位。
