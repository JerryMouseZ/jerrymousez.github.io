Claude 追溯 NIST ECDSA 曲线种子来源 ⭐️ 8.0/10

Anthropic 研究称，Claude 在不到半小时内追溯出 NIST P-192、P-224、P-256、P-384、P-521 五条 ECDSA 曲线的种子来源：它们并非由哈希算法生成，而是 C 库 lrand48 随机数生成器以 Unix 时间戳为种子产生的输出。另有一个二进制种子 B-163 未能匹配任何已尝试的方法，仍无法解释。该结论来自 Anthropic 的研究报告，尚非独立复现的测量结果。

hackernews · ahlCVA · 10月16日 18:55 · 社区讨论

「背景」 NIST 的 P-192、P-224、P-256、P-384 和 P-521 椭圆曲线于 2000 年通过 FIPS 186-2 数字签名标准引入，其种子由 NSA 在 1997 年提供，但生成方法长期未公开。Filippo Valsorda 为此设立了 12,288 美元的 NIST 椭圆曲线种子悬赏，征集破解这五个种子的方案。

「实际影响」 这一结果说明这些曲线的生成过程依赖可预测的时间戳种子，而非此前设想的哈希派生方式；但正如评论所指出的，它只能确认生成方法，无法排除曲线在生成后被筛选或丢弃候选的可能，因此不能据此证明曲线未被刻意挑选。对使用这些曲线的系统而言，现有安全性结论不因此直接改变。

「社区讨论」 有评论者指出，确认生成方式并不等于确认选择过程，因为生成后丢弃的候选无法被观察，理论上仍可通过遍历时间戳来筛选具有特定性质的曲线。另有评论推测，未解释的 B-163 种子可能是发布过程中某位数字被误写所致。

hackernews · rs_rs_rs_rs_rs · 10月16日 14:44 · 社区讨论

「背景」 该漏洞可追溯到最初的 BSD 源码：SysV 共享内存附加计数器使用有符号 16 位 short，攻击者通过 fork 259 个进程使其溢出，再配合 IP 组播选项处理中的越界写和竞态条件实现本地提权。据外部报道，相关缺陷在概念验证代码于 2026 年 10 月 16 日发布后已被修补。

「社区讨论」 有评论者认为，这个漏洞能在被高度审计的代码库中存活 37 年，说明部分内核漏洞很难仅靠人工审查发现，并由此提出疑问：模糊测试或静态分析能否现实地发现这类漏洞，还是必须依靠人类思考利用原语。另有评论者指出，NetBSD 在 1999 年 8 月重写该段代码时似乎意外修复了它。

JPEG XL 与 AVIF 网页图像对比：编码器速度与成熟度之争 ⭐️ 7.0/10

Jake Archibald 发布了一篇针对网页图像交付场景的 JPEG XL 与 AVIF 详细对比分析。文章指出，libjxl 在最高压缩档位下速度极慢：相比默认设置，照片文件仅缩小 2–7%，截图和插画约缩小 25%，但耗时 9–46 秒，是默认设置的 50–180 倍；而 jixel 能在数秒内得到相同结果。评论者补充称，libjxl 在 effort 大于 7 时的慢速主要源于对 Butteraugli 感知误差指标的迭代评估优化循环。该文属于对现有编解码器的分析，而非新版本发布或实测基准的官方声明。

hackernews · farlight · 10月16日 16:12 · 社区讨论

「背景」 JPEG XL 与 AVIF 都是面向网页图像交付的新一代编解码格式，但两者的浏览器支持情况并不相同。根据 Can I use 的 AVIF 支持表，AVIF 已获得主流浏览器支持；而一篇 2026 年的 JPEG XL 指南称，Safari 是当时唯一支持 JPEG XL 的浏览器。这一支持差异是讨论两种格式在网页场景下如何取舍的前提。

「实际影响」 对需要在网页上选择图像格式的工程师而言，这意味着 JPEG XL 的压缩优势高度依赖编码器实现和 effort 设置：追求极致体积会带来数十秒级的编码延迟，不适合在线或批量实时转码流程。评论者还指出，换用更好的编码器后，文中 Firefox 截图的无损 JXL 可从 66.9kB 降至约 40.7kB（缩小 39%），猫插画可从 255.3kB 降至 178kB（缩小 30%），说明当前工具链的编码器质量仍是选型时需单独验证的变量。

「社区讨论」 有评论者以 MP3 时代 LAME 编码器多年才成熟为例，主张不要急于宣布某一格式胜出，并提醒 WebP 当年也曾被过度宣传。另有开发者分享了自己在生产中使用 AVIF 的 ffmpeg 参数组合，称在 2K 以内图像上可实现 10 倍以上体积缩减并保留透明通道，但强调这是其个人调优经验而非通用结论。

Mercor 分析称九成美国工时任务缺乏 AI 基准覆盖 ⭐️ 7.0/10

Mercor 的 labor-index 分析将现有 AI 基准与职业任务数据对照后声称，约 90% 的美国工作小时用于现有基准覆盖很少或完全没有覆盖的任务，因此难以判断 AI 对这些工作的实际能力。该结论来自单一来源的分析，而非独立测量或已发布的产品能力；其“覆盖良好”的判定标准和任务分类方法在社区中受到质疑。

hackernews · speckx · 10月16日 17:08 · 社区讨论

「背景」 该分析将现有 AI 基准的覆盖范围与美国职业任务数据（评论中提及 O*NET）进行对照，以判断哪些工作内容有可用的评测。O*NET 是美国劳工部维护的职业信息数据库，常被用于职业与任务分类，但评论者指出它更新滞后、缺少部分现代白领职业，且任务描述未必贴合实际工作。因此，基准覆盖率的结论在很大程度上取决于任务分类体系的选择与“覆盖良好”的判定标准。

「影响」 该分析若成立，意味着仅凭现有基准分数难以推断 AI 在多数实际岗位上的可用性；评估者需要按具体职业任务补充覆盖，而不是把通用基准排名当作部署依据。不过，由于“覆盖良好”的判定标准和 O*NET 任务分类本身存在争议，这一 90% 数字应视为该机构的方法论结论，而非独立验证的测量结果。

「社区讨论」 评论者普遍认同方向性结论，但集中批评方法：purplepatrick 指出 O*NET 缺少金融、科技、咨询等现代白领职业，且任务集常与实际工作不符；OtherShrezzing 认为“覆盖良好”实际只等同于“有覆盖”，例如用 13 条提示代表社会工作者辅导父母的工作显然不足。gregwebs 则质疑按职业类别推断覆盖度的做法，认为 AI 同样可能完成法律秘书和法庭书记员的电脑工作。

Rust 框架 DenseCore 在 CPU 上逐位复现 PyTorch 训练 nanoGPT ⭐️ 7.0/10

一名计算机专业学生发布了 DenseCore，这是一个用 Rust 编写、提供类 PyTorch Python API 的小型深度学习框架。作者称，将 `import torch` 指向该框架后，Karpathy 的 nanoGPT 无需改动即可运行，在 Apple Silicon Mac 的 CPU 上，初始权重、损失、梯度和权重在测试的 50 步内与 PyTorch 逐位一致，开启 dropout 时也相同。为做到这一点，作者处理了 PyTorch CPU 注意力实际走 flash-attention 内核、dropout 开启时切换路径、Adam 尾部循环舍入差异以及 `clip_grad_norm_` 用倒数乘法代替除法等数值细节。作者同时指出，PyTorch 自身跨机器并不一致：同一版本下 Mac 与 Linux x86 上测试的 26 个算子中仅 1 个结果相同，因此 DenseCore 目前只在与 PyTorch 相同的 Apple Silicon Mac 上匹配。该框架体积约 2 MB，而 PyTorch 约 580 MB；以上均为作者自述，尚未经独立验证。

reddit · r/MachineLearning · /u/Mental-Feature-2377 · 10月16日 18:49
