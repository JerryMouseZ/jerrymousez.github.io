eMudhra 八个中间 CA 私钥泄露，各平台需更新证书列表 ⭐️ 9.0/10

eMudhra 八个中间 CA 证书的私钥已被泄露，这些证书链到 Mozilla、微软、苹果和 Chrome 根程序以及众多下游信任库所信任的根证书。任何内置受信任证书列表的软件都需要更新：Linux 发行版需更新 ca-certificates 包，Python 生态中 uv 0.13.4、pip 26.2.2 和 certifi 2026.10.19 已发布包含更新证书列表的版本。该事件由 we-have-a-problem.com 通过 GitHub 仓库跟踪各软件更新进展。

rss · Simon Willison · 10月20日 23:50

「背景」 中间 CA 证书由受信任的根 CA 签发，用于代表根证书签发终端证书；一旦其私钥泄露，攻击者便可签发看似由受信任根背书的伪造 HTTPS 证书。据 Mozilla 安全博客，Mozilla 于 10 月 17 日 20:06 UTC 收到报告，称八个 eMudhra 中间证书的私钥已泄露，这些密钥可能被用于为攻击者并不控制的网站签发欺诈性 HTTPS 证书。

「影响与应对」 依赖内置证书列表的软件需要更新，否则仍会信任已泄露的中间 CA。Linux 发行版需更新 ca-certificates 包；Python 用户应升级至 uv 0.13.4、pip 26.2.2 或 certifi 2026.10.19，其中 certifi 已移除 emSign 根证书。评论者 xucheng 指出，自行内置 CA 存储的软件难以逐一修补，相关系统可能长期处于风险中。

「社区讨论」 有评论者指出，八个“被泄露”CA 的私钥实际上都只有一个字节，其中一个私钥字面值就是“4”，因此对“泄露”一词表示质疑。另一位评论者 galadran 表示影响分布极不均衡：Mozilla 十多年前推出的 OneCRL 让 Firefox 用户在数小时内自动获得保护、无需更新，Chrome、苹果和微软也有类似机制，但生态其余部分在吊销机制上投入甚少。还有评论者 xucheng 指出，许多软件各自内置 CA 存储，系统 CA 包容易修补，但逐个修补内嵌证书的二进制文件非常困难，因此不少系统将长期处于脆弱状态。

Google 开源 TorchTPU：TPU 获得原生 PyTorch 后端 ⭐️ 8.0/10

Google 已在 GitHub 开源 TorchTPU，为 TPU 提供原生 PyTorch 后端，使 TPU 成为与 GPU、CPU 并列的 PyTorch 运行目标。据社区转述的 Google Cloud 说法，该项目与 Meta 的 PyTorch 团队共同开发，现有 PyTorch 代码几乎无需改动即可运行，vLLM、SGLang、llm-d、TorchTitan 等框架已接入，Hugging Face Transformers v5 可直接将模型部署到 TPU。上述性能与兼容性说法来自项目方和社区转述，所给材料中没有独立验证或具体基准数据。

hackernews · ilreb · 10月20日 16:40 · 社区讨论

「背景」 此前 PyTorch 在 TPU 上主要依赖 XLA 桥接，用户常需处理编译与适配问题。TorchTPU 由 Google 与 Meta 的 PyTorch 团队共同开发，提供原生后端，支持 eager 模式调试并通过 torch.compile 优化 TPU 利用率。

「对开发者的实际影响」 现有 PyTorch 代码迁移到 TPU 的门槛明显降低：据外部报道，Hugging Face Transformers v5 可通过 device_map="tpu" 直接部署到 TPU，Diffusers 支持 eager、torch.compile 和张量并行，vLLM-TorchTPU 与 SGLang-TorchTPU 则保留上游调度器和 API 服务层。不过这些集成细节来自二手报道，Google 官方尚未在所提供的材料中给出性能数据，实际可用性和性能仍需自行验证。

「社区讨论」 有开发者指出，Amazon 已为 AWS Trainium 提供类似的 torch-neuronx 后端，说明各家加速器都在补齐 PyTorch 原生支持。另有评论者称自己基于 Tenstorrent 软件栈开发了开源 libtpu 实现，已能运行大部分 TorchTPU，并认为这展示了把 PyTorch 下沉到 tile 类加速器的完整环节。也有人认为 XLA 可能成为比 inductor 更好的编译基础设施，从而惠及更多硬件，并称这基本宣告 TensorFlow 出局；还有用户回忆过去需费力让 PyTorch 跑在 TPU 上，认为如今硬件细节多集中在 Pallas 或 CUDA 等内核层，JAX 与 PyTorch 之争更接近风格偏好。

Cloudflare 发布 tsrs：TypeScript 的 Rust 移植版 ⭐️ 8.0/10

Cloudflare 博客介绍了 tsrs，这是用 Rust 重写的 TypeScript 编译器移植项目。据社区评论，该项目采用一种特殊内存模型：对长生命周期对象使用永不释放的 arena，以模拟 GC，从而绕开 Rust 没有垃圾回收、直接移植 GC 语言通常需要重构数据结构的障碍。评论还称，项目动机之一是获得可在仅支持 WASM 的沙箱中运行的 TypeScript 编译器，而现有方案需把 tsc 编译为 Go 再导出到 WASM，会带上完整 Go 运行时；据称 Rust 版本比参考 tsc/Go 实现更快。上述性能与动机说法来自博客和评论，并非独立测量结果。

hackernews · hnisjafx40 · 10月20日 13:18 · 社区讨论

「背景」 tsrs 是 Cloudflare 与 VoidZero 合作推进的 TypeScript 编译器 Rust 移植项目，由 Max Schwenk 构建，并以实验性项目的形式纳入 Oxc JavaScript 编译器工具链，同时与 TypeScript 团队密切协作。据 Cloudflare 博客介绍，其目标是减少开发者等待代码检查的时间。社区讨论指出，这一移植的动因之一是获得一个能在仅支持 WASM 的沙箱中运行的 TypeScript 编译器，而 Rust 没有垃圾回收，项目因此采用永不释放的 arena 来模拟 GC。

「影响与关注点」 TypeScript 团队成员 DanRosenwasser 表示，团队正与维护者合作，弄清 tsrs 为何快、哪些优化是安全的，并称其初步判断是速度不只取决于语言选择，TS 7.1 的部分提速也来自优化。对考虑采用该工具的用户而言，arena 永不释放意味着内存占用会随长生命周期对象增长，需关注其内存模型是否可靠以及实际负载下的表现。

「社区讨论」 评论者 afdbcreid 认为，用永不释放的 arena 伪造 GC 是该项目绕开 Rust 无 GC 难题的关键，并希望这一做法在内存安全上站得住脚。sheepscreek 则指出，项目初衷并非单纯追求更快的 Rust 编译器，而是需要能在 WASM 沙箱中运行的 TypeScript 编译器，速度提升只是附带结果。egonschiele 对速度提升表示期待，但对博客所称“前沿 AI 模型几乎可独立完成大规模移植、作者零代码”表示保留。

OpenAI 称新模型大幅提升 COBOL 等低资源语言能力 ⭐️ 8.0/10

OpenAI 在官方博客中称，其最新模型显著提升了 COBOL、Fortran 和 Visual Basic 等低资源编程语言的开发与迁移能力。据 Telegram 摘要转述，在“用 20 种语言从零构建 SQLite 引擎”的测试中，GPT-6 Astra 的平均通过率从 GPT-5.6 Sol 的 26.8% 升至 87.4%，低成本型号 GPT-6 Luna 为 40.3%，API 成本下降 78%。在把老旧 COBOL 代码迁移到现代语言的测试中，GPT-6.1 Sol 在低推理强度下准确率从 5.4% 升至 86.6%、成本降低 39%，高推理强度下达到 97.9%。相关评测集已在 GitHub 开源；上述数字均来自 OpenAI 的公告转述，尚无独立复现或详细方法说明。

telegram · zaihuapd · 10月20日 14:24

「背景」 低资源编程语言指 COBOL、Fortran、Visual Basic 等训练语料相对稀少的语言，其中 COBOL 仍大量存在于银行、保险等机构的遗留系统中，把这类代码迁移到现代语言长期依赖人工。OpenAI 此次以 MultiLangBench 多语言基准和 COBOL 迁移测试来量化模型在这类语言上的表现，并开源了相关评测集。

「影响」 若这些数字成立，COBOL 等遗留系统的迁移评估将更多依赖可复现的公开评测集，而非厂商单方声明；计划采用该能力的团队应先核对 GitHub 上评测集的任务定义与评分口径，并在自有代码库上验证，因为低推理强度与高推理强度之间准确率差距明显，成本与准确率的取舍会直接影响迁移方案。

Humming：面向量化推理的快速灵活内核库 ⭐️ 7.0/10

rss · vLLM Blog · 10月21日 00:00

「背景」 随着模型规模增长，内存容量、带宽和计算成本成为部署瓶颈，MoE 模型尤为突出——DeepSeek-V3 有 6710 亿参数，但每 token 仅激活 370 亿。量化通过降低权重和激活精度来减少存储与数据搬运，但不同模型和 GPU 代际对量化方案的需求各异（WNA16、W8A8、W4A8、W4A4，以及 INT4、NVFP4 等不同数值格式和缩放粒度），为每种组合单独开发内核会带来不断增长的维护负担。

「方案」 Humming 的核心思路是将量化描述与执行选择分离，并用共享 CUDA 组件组合内核。它先把不同导出格式统一为 Humming 标准格式，将权重格式、缩放粒度、缩放数据类型、零点等作为独立参数描述，激活也有自己的数值格式和量化设置，从而让分组 INT4 权重可搭配 BF16 激活。执行时由三层配置描述内核：Layer Config 描述张量形状、数据类型和量化参数；Compute Config 指定 GEMM 类型和计算选项；Tuning Config 选择 tile 形状、流水线级数、warp 特化、内存访问和 MMA 指令等。默认由设备相关启发式选择配置，并可为不同输入尺寸范围准备多个内核在运行时调度——小 batch 下 cp.async 加 MMA 的多级流水线可能优于 TMA/UMMA，大 batch 下则相反。CUDA 层面，任务调度、数据搬运、反量化与缩放、Tensor Core 计算和输出处理被组织为可复用组件，JIT 编译按配置组合组件并消除未用分支，新格式或架构只需扩展相关组件。作者报告在 H200、CUDA 13.4 下单 W4A16 内核编译时间从 CUTLASS 配 NVCC 的 23.35 秒降至 Humming 的 1.82 秒（NVCC）或 1.88 秒（NVRTC），关闭编译缓存；模型预热时并行编译单层 GEMM 所有 M 尺寸的内核约需 2–4 秒。性能方面，作者自报的微基准覆盖 M 从 1 到 8192 的每个 2 的幂，冷 L2 缓存、内核充分预热后独立计时。W4A16 密集场景下 Humming 在多数配置匹配或超过 vLLM Marlin，小 batch 在多个设备上约 3–4 倍加速，大 batch 在 H200 上约为 Marlin 的 2 倍、部分 B300 场景超过 3 倍；MoE 场景下 MXFP4 W4A16 在 H20/H200 中大型 batch 约为 Marlin 的 2 倍，B300 上 Grouped 路径约 5 倍。W8A8 在 H20/H200 小中 batch 约为 DeepGEMM Contiguous 的 2.6 倍和 2.5 倍。端到端在八卡 H20、TP=8 上运行 DeepSeek-V4.1-Flash，将 MoE 从 Marlin W4A16 换成 Humming W4A8 后，吞吐提升约 14%–43%，TTFT 降低约 25%–32%，并发 64 时输出吞吐从 442.37 升至 633.94 tokens/s。Humming 还支持 Turing 以来的 NVIDIA 架构及 T-Head 真武 810E，并利用 Blackwell Tensor Core 未在 PTX 类型系统中暴露的 float4e0m3 和 float8e3m4 原生格式；但 Rubin 不支持这两种隐藏格式。作者也指出，SM103 的 UMMA 不再支持 INT8，只能回退到性能低得多的早期 MMA 指令。上述结果均为社区自报微基准，基线和测试方法仅简要说明，尚未经独立验证，端到端收益也主要来自单一模型和硬件配置。

「启示」 Humming 表明，把量化语义描述与内核执行策略解耦、再用可组合的 CUDA 组件和 JIT 特化来覆盖格式与硬件差异，可以在控制维护成本的同时获得有竞争力的量化推理性能。不过其加速数据目前仍以作者自报的微基准为主，更广泛的端到端影响有待后续验证。

英国竞争与市场管理局（CMA）提出方案，要求苹果向通用非接触支付标准开放 iPhone 的 NFC 与钱包权限，并大幅降低收费，指其规则阻碍英国金融科技企业创新。CMA 称英国 39%的支付已是非接触支付、Apple Wallet 最受欢迎却无竞品，咨询期至 2026 年 11 月 17 日；苹果反对该方案，称现有安排已能让开发者在应用内安全提供非接触交易。

telegram · zaihuapd · 10月21日 02:52

「背景」 英国竞争与市场管理局（CMA）此前已就 iPhone 的 NFC（近场通信，即手机贴近读卡器完成支付的技术）访问问题公开征集意见，此次是在该基础上提出的拟议行为要求，并进入公开咨询阶段。

「潜在影响」 若该提案最终生效，英国的金融科技公司和支付服务商将可直接调用 iPhone 的 NFC 与钱包功能，推出与 Apple Wallet 竞争的非接触支付产品；目前这类权限仅向苹果自家钱包开放。该方案仍处咨询阶段（至 2026 年 11 月 17 日），尚未定案。
