Linux IPv4 TCP 释放后使用漏洞 CVSS 9.8 ⭐️ 8.0/10

Linux IPv4 TCP 栈存在一个释放后使用（use-after-free）漏洞，编号 CVE-2026-98432，CVSS 评分 9.8。社区讨论指出，该漏洞不要求启用 MPTCP，属于通用型释放后使用问题；成功利用需要多个 CPU 核心参与数据包处理，单核系统或将包处理绑定到单核的系统不受影响。讨论还称，通过互联网直接利用的可能性不高，因为多数 ISP 路由器会丢弃带 IP options 字段的数据包；按 Red Hat 的说法，自行丢弃带 IP options 的数据包有帮助，但不构成完整缓解。评论提到 Ubuntu 与 Red Hat 当时尚未发布补丁。

hackernews · oger · 10月31日 19:16 · 社区讨论

「背景」 该漏洞位于 Linux 内核 IPv4 TCP 握手路径，影响 4.4 及之后的内核版本；据 AWS 安全公告，远程未认证攻击者可向受影响的监听端口发送构造的 IPv4 TCP 数据包，在特定条件下触发未认证远程代码执行。Red Hat 的安全公告将其描述为 TCP 连接请求处理过程中的竞态条件所导致的释放后使用（use-after-free）。

「实际影响」 在 Ubuntu 和 Red Hat 尚未发布补丁的情况下，受影响主机可先采用 Red Hat 发布的 RHSB-2026-016 临时缓解措施；有社区工具可检查 Ubuntu 主机并协助应用该缓解。评论指出，自行丢弃带 IP 选项的数据包只是部分缓解，并非完整修复，且成功利用需要多核并行处理数据包，单核或数据包处理绑定单核的系统不受影响。

「社区讨论」 有评论者批评 HN 编辑标题时删去“Linux”，认为这会误导非 Linux 用户，因为 BSD、macOS 和 Windows 不受影响。另有评论质疑 Ubuntu 和 RHEL 作为主打服务器场景的系统为何迟迟未修复；还有人指出，在 AWS 负载均衡器之后、按最佳实践不直接接收不可信 TCP 连接的用户，受影响程度可能较低。

Jepsen 审计 ParticleDB 1.1.4：发现严重事务安全违规 ⭐️ 8.0/10

Jepsen 对 ParticleDB 1.1.4 的审计发现，该版本在几乎每一项可测量的维度上都出现了严重的事务异常，包括已提交写入丢失、内部一致性违规、G1a（Aborted Read）、G1b（Intermediate Read）和 P4（Lost Update）；在追加负载中，成功追加的值会从后续读取中消失。Jepsen 共报告了 96 个问题，从崩溃、死锁、数据丢失，到无法删除的部分不可见行、`WHERE 4 = 5`、被删除的表以扭曲形式重新出现、列混淆、字符串变成整数等。ParticleDB 官网曾宣称其经过 TLA+ 形式化证明，但 Jepsen 表示在合作期间并未获得任何 TLA+ 规范，因此无法确认所证明的性质，也无法确认这些性质是否对应实际构建的 ParticleDB。基于问题的严重程度和产生过程，Jepsen 建议用户停止进一步部署 ParticleDB，并尽快迁移到其他数据库，同时尽可能从更可靠的来源检查或重建数据库状态。

hackernews · aphyr · 10月31日 13:39 · 社区讨论

「背景」 Jepsen 的测试针对的是 ParticleDB 1.1.4 所宣称的隔离级别：据其分析页面，该版本自称兼容 Postgres，并通过 occ-v3 与 zero-copy-occ 事务模式提供快照隔离，通过 serializable-ssi 提供可串行化，通过 table-2pl 提供强可串行化。Jepsen 是一套以黑盒方式对分布式数据库施加并发事务负载、检验其是否满足所宣称一致性保证的测试框架，因此本次结论直接针对这些宣称的隔离级别。

「对用户的影响」 对于已经部署 ParticleDB 1.1.4 的团队，Jepsen 的建议是停止继续部署并迁移，这意味着需要评估现有数据的完整性，并考虑从其他可靠来源重建状态。由于该版本宣称兼容 Postgres，依赖这一兼容性进行迁移的用户需要重新验证目标数据库上的数据与行为。

「社区讨论」 有评论者将这一结果归因于“用 AI 氛围编程”写数据库，并引用 Jepsen 的迁移建议；也有评论者提出软件可分为“构造上正确”和“构造上不正确”两类，后者往往靠运气和在代码路径中绕过错误设计来运行，而 AI 在寻找插入变通办法的位置上可能相当有效。另有评论者特别指出，官网宣称的 TLA+ 形式化证明与实际无法获得规范之间的落差。

研究人员披露可接管 ChatGPT 账户的漏洞链 ⭐️ 8.0/10

Parameter Labs 披露了一条针对 ChatGPT 前端 HTML 预览（原 Canvas）沙箱的漏洞链：沙箱 iframe 可通过 postMessage() 触发父页面 MathLive 虚拟键盘，而接收端使用 innerHTML 注入内容，且未限制其他沙箱帧调用；攻击者借此注入无沙箱限制的新 iframe，再借 CSP 白名单中的 YouTube oEmbed 端点反射执行 JavaScript，最终读取用户私有数据并通过图片请求外传。OpenAI 确认两个前端均拒绝了所报告的消息，已修复问题并支付总计 5,000 美元赏金。攻击需要受害者点击分享链接，且仅影响已登录用户。

hackernews · armcat · 10月31日 10:30 · 社区讨论

「背景」 ChatGPT 的 HTML 预览（前身是 Canvas）会把交互式自定义 HTML 应用放在沙箱 iframe 中运行，其安全前提是这些 iframe 无法与 OpenAI 的 API 或用户私有数据交互。Parameter Labs 的披露显示，OpenAI 在图表功能中使用的 MathLive 数学输入库自带虚拟键盘，父页面会通过 postMessage() 接收来自 iframe 的触发消息，而这段接收代码使用 innerHTML 写入内容，且未校验消息来源。

「影响与应对」 该漏洞意味着恶意构造的 ChatGPT 分享链接可在已登录用户点击后以其身份执行操作或窃取私有数据，因此用户应谨慎打开来源不明的分享链接。对开发者而言，此案例说明沙箱 iframe 与父页面之间的 postMessage 通信、innerHTML 注入以及 CSP 白名单中的第三方端点（如 YouTube oEmbed）都可能成为绕过隔离的环节。

「社区讨论」 有评论者认为 5,000 美元赏金对如此严重的漏洞偏低，可能打击其他研究者的报告意愿；也有人指出文章写作风格使攻击链难以理解，例如 JSONP 部分更像在解释机制而非绕过方式。另有评论将此漏洞与 ChatGPT 桌面应用“Work”聊天可远程访问文件系统的问题联系起来，认为整体风险值得关注。

HackerTube：用 HN 评论推荐视频搭建的 YouTube 界面 ⭐️ 7.0/10

Andrej Karpathy 发布了 HackerTube（hackertube.org），一个以 YouTube 式界面呈现视频的网站，视频来源是 Hacker News 评论中推荐的链接。据项目说明，它汇集了自 2007 年以来 39,834 条 HN 评论中提到的 6,454 个视频，不设算法推荐或互动指标，由社区讨论充当筛选机制。这是一个个人侧项目，而非 YouTube 的替代产品或正式发布的功能。

hackernews · karpathy · 10月31日 19:56 · 社区讨论

「背景」 Hacker News 的评论长期被用来分享技术讲座、演示和纪录片等视频链接，但这些推荐散落在讨论串中，难以集中浏览。HackerTube 把这些链接抽取出来，套上类似 YouTube 的浏览界面，让用户按社区推荐而非平台算法来发现内容。

「影响」 对想找技术类视频的读者来说，这是一个可直接浏览的替代入口，但内容范围受限于 HN 评论中出现过的链接，且项目本身未说明视频可用性、排序或更新机制。有评论者已基于它搭建了加入艺术、文化、电影制作来源的自用版本，说明其数据与界面思路可被复用。

「社区讨论」 多位评论者认为，相比 YouTube 的推荐流，这种浏览体验更少被诱导点击，有人形容它像 2010 年前后的信息流质量。也有人指出，自己上网的目的正是接触算法推荐之外的新鲜内容，而按兴趣定制的信息流反而削弱了这种探索感；另有评论者希望增加按新旧排序的功能。

快慢两条路：如何摆脱“好项目总给别人”的循环 ⭐️ 6.0/10

rss · Sean Goedecke · 11月1日 00:00

「背景」 在科技公司里，想获得好声誉就需要参与重要项目，但参与重要项目又往往需要先有好声誉，这让不少工程师陷入“永远坐冷板凳”的困境。作者认为，问题的根源不在正式流程，而在于管理者的真实激励：他们更在意自己能否交付，因此倾向于把高风险的高曝光项目交给已知可靠的人。

「方案」 作者把这种局面称为“科技公司心智理论”：理解驱动决策的真实激励，而非正式流程。管理者并非不关心下属发展，但更关心自己的声誉；高曝光项目一旦失败，最容易损害管理者声誉，而大厂管理者平均任期只有几年，短期避险对他们而言是理性的。于是形成恶性循环：越依赖某个人，这个人越可靠，其他人越缺乏经验、越不可靠。

慢速路径是经典的“棘轮效应”：稳定交付小而低风险的工作，主动向管理者和团队沟通成果，用积累的声誉换取稍高风险的任务，同时避免任何会被视为不可靠的错误，最终被视为可以安全托付重要工作的人。作者强调，这条路不靠说服管理者“这不公平”或“我需要发展机会”，因为管理者的激励无法被改变，只能让自己看起来与他们的激励一致。缺点是太慢，可能耗时数月甚至数年，期间可能遭遇无法避免的失败、管理者离职或技术环境变化。

快速路径则伴随风险。其一是与跳过直属上级的更高层建立关系：如果上级的上级认为你很强，会直接建议你的管理者把项目交给你，而管理者也会理性地顺水推舟，因为搞砸了责任不在自己。但高层管理者政治嗅觉敏锐，刻意推销容易适得其反，最可靠的方式仍是长期可靠地为他们提供价值，这又回到了慢速路径。其二是“侧注”：自己发现并实现重要项目，制造出无需被分配的工作。风险是项目可能失败或并不重要，白费时间，而且不少管理者会反感，因为这让他们在会议上显得不了解团队在做什么。其三，也是最有效的快速路径，是让工程师同事认可你。管理者离一线较远，只能依赖结果这种慢速代理来判断技术能力；工程师则能快速形成判断，几次“你看到了我没看到的东西”就足以让人认定你很强。在健康团队里，同事会告诉管理者，你就能更早获得重要工作；但在糟糕的团队里，同事可能识别不出强人、不愿沟通，甚至因为视能干的同事为威胁而主动诋毁。

「启示」 作者的核心结论是：如果好项目总落到别人手里，你面对的是声誉问题，而非公平问题；科技公司本就不以公平为目标，而是以赚钱为目标。与其在 1:1 中抱怨不公，不如设法让管理者看起来“把工作交给你符合他们的利益”——无论是借助更高层、自创项目，还是在管理者信任的工程师中建立声誉。
