开发者将 Wine 移植到 OpenBSD ⭐️ 7.0/10

一位开发者已将 Wine 移植到 OpenBSD，并在 openbsd-ports 邮件列表中说明了这一移植工作。据邮件列表讨论，该移植包含针对 OpenBSD 的兼容性改动，例如 %gs 桩（%gs stubs）和 SIGUSR1 处理；作者表示，由于这些改动被明确标记为仅适用于 OpenBSD，预计不会有太多内容合并回上游。目前可确认的是移植与相关讨论已经存在，但来源未提供版本号、可用性范围或独立测试结果。

hackernews · iamnothere · 10月19日 13:35 · 社区讨论

「背景」 Wine 是一个在类 Unix 系统上运行 Windows 程序的兼容层，此前长期未能在 OpenBSD 上使用。据 Adafruit 的报道，主要障碍在于 OpenBSD 不允许用户态设置 %gs/gsbase，移植者通过模拟 %gs 前缀等方式绕过了这一限制。

「影响」 对 OpenBSD 用户而言，这意味着在 OpenBSD 上运行 Windows 程序多了一条由社区维护的途径；但由于改动被标记为 OpenBSD 专用，其他平台不会自动受益，上游合并前景也有限。

「社区讨论」 评论者 t-3 引述了作者的说法：许多更新在技术上也能在其他操作系统上运行，但作者为简化工作而将 OpenBSD 相关改动全部标记为仅限 OpenBSD，因此预计上游合并有限。另有评论者 RunSet 认为，在 OpenBSD 日益被视为“slopcode”避风港的当下，这一消息尤其受欢迎；其余评论多为玩笑或无关链接。

Mac.apk 让 Android 应用在 Apple Silicon Mac 上原生运行 ⭐️ 7.0/10

开源项目 Mac.apk 旨在让 Android 应用在 Apple Silicon Mac 上原生运行，不依赖模拟器、虚拟机或底层 Linux 层。该项目由 kksimp 发布在 GitHub 上，目前仅有仓库和 Hacker News 讨论作为证据，尚无独立测试或性能数据。

hackernews · flocked · 10月19日 16:45 · 社区讨论

「背景」 Mac.apk（相关发布页也称 MacDroid）的目标是让 Android APK 直接作为普通 macOS 进程在 Apple Silicon Mac 上运行，应用代码直接跑在 CPU 上、由 Mac 的 GPU 渲染，而不是依赖模拟器或后台运行的 Android 系统。项目方在测试招募帖中称，每个应用会作为独立应用安装到“应用程序”文件夹。

「实际影响」 评论指出，应用数据被存放在 .app 包内部而非 Application Support 目录，项目在 wiki 中解释这是为了避免文件散落在用户主目录；这种做法会影响备份、权限管理和应用更新时的数据处理。此外，对 Google Play Services 的依赖可能限制可运行应用的范围。

「社区讨论」 有评论者认为，这一方案对 Mac 上的 Minecraft 玩家有实际价值：移动端和主机端玩家只能使用 Bedrock 版本，在 Mac 上运行 Android 版即可与本地主机玩家联机或加入 Bedrock 服务器。另一些评论则批评项目介绍文案带有明显的 AI 生成句式，并对 AI 生成的技术文字表达反感。

Hacker News 上一条 Ask HN 帖子引述了一位 Meta 工程师在 LinkedIn 上的自述：用 AI 写代码后，系统像“黑盒”，逐行审查又耗时过长，因此可能交付自己只懂高层、不懂细节的代码。发帖者询问其他工程师如何处理这一问题。该讨论获得 301 分、445 条评论，评论者提出了设计先行、强制人工审查、以测试弥补理解缺口等具体做法，但均为个人经验与观点，并非经过验证的行业标准。

hackernews · rzk · 10月19日 11:24

「社区讨论」 bitwizeshift 表示自己不让 LLM 设计代码，而是先画出抽象与角色的完整结构，再让模型实现空缺部分；jedberg 以 Principal Engineer 的经验类比，认为人负责设计、AI 像初级工程师一样实现细节。ChrisMarshallNY 则称自己把省下的编码时间用于大量交互式测试，并指出发现的多是实现错误而非编码错误；plastic041 批评部分评论在回避阅读自己负责的代码。

Plex 漏洞遭野外利用，植入挖矿程序 ⭐️ 7.0/10

据安全博客报道，Plex 的多个漏洞正被在野利用，攻击者借此在用户服务器上安装加密货币挖矿程序及其他载荷。社区成员报告了多起真实感染案例，并提到一个名为 Plex2Shell 的概念验证利用链，据称由大语言模型串联多个 CVE 构成。目前尚无官方确认的受影响版本范围或修复状态，相关细节主要来自博客与用户自述。

hackernews · mindracer · 10月19日 13:36 · 社区讨论

「背景」 Plex 此前已发布安全更新，要求运行 Plex Media Server 1.43.2 或更早版本的用户升级到 1.43.3 或更新版本，以修复多个安全问题。评论中提到的 Plex2Shell 是一个概念验证利用程序，据称通过串联多个 CVE 实现攻击，这也解释了为何未及时升级的旧版本实例会成为目标。

「影响与应对」 自建 Plex 服务器的用户面临实际风险：多名评论者称其 CPU 被占满、Plex 无法使用，随后发现名为 MyLovelyMiner 或 icloud-services 的异常进程。有用户因错过升级邮件或未察觉 apt 仓库地址变更而长期运行旧版本，因此及时核对 Plex 版本并更新软件源是当前可采取的防护措施。

「社区讨论」 多名评论者报告了亲身感染经历，包括 Linux 和 Mac mini 环境，并指出攻击者将挖矿进程命名为 MyLovelyMiner 等显眼名称，反而容易被发现。NelsonMinar 提到 Reddit 上还有 DDoS 节点等其他载荷的报告，并将 Plex2Shell 概念验证视为这波攻击的源头；另有评论者则借机批评 Plex 新版界面性能，称已转向 Jellyfin。

科技博客

用“艺术”为技术辩护为何难以说服公众 ⭐️ 5.0/10

rss · Sean Goedecke · 10月20日 00:00

「背景」 有人主张编程、数学等技术领域本质上是艺术，因此不应让 LLM 介入。作者 Sean Goedecke 认为，这类论证在工程师圈子里或许动人，却难以说服普通公众和技术雇主，因为它动摇了公众支持这些领域的隐含理由。

「方案」 作者先重构了公众的心理链条：普通人享受现代医药、交通、手机等技术成果，知道数学和编程对维持并推进这些技术不可或缺，于是愿意尊重数学家的“神秘研究”，也接受软件工程师获得可观薪酬。换言之，公众看重技术领域，是因为看重科学，而看重科学又是因为看重技术；他们只会在“艺术最终有助于研究者产生推动科学前沿的创造性洞见”这一限度内容忍艺术说法。若工程师说“LLM 能加速解题，但真正的意义是创造伟大艺术，所以我反对使用”，公众会觉得受骗，如同雇人装修却被要求全程手工以体验“创造的乐趣”；对技术雇主而言，这种论证更缺乏说服力。作者承认自己认同编程和数学可以很美，也认为几乎一切事物都可能有艺术维度，但这不足以构成公共论证。他建议把艺术价值与实用技术价值挂钩，例如：优秀软件依赖优雅抽象，需要人的创造触感；数学进步依赖创造新抽象，而 LLM 尚不擅长；技术进展不均匀，需要灵感与“吊床时间”；伟大软件需要人类灵感，而伟大软件推动领域前进。不过作者对这些论点持保留态度：他尚未见到 LLM 生成的代码库真正撞墙，也不认为 LLM 必然无法创造新抽象或产生类人灵感，还质疑伟大产品是否必须配伟大代码——服务好想法的工匠式代码为何不够？他还指出，赖特流水别墅的保温施工其实有严重霉变问题，却未影响其艺术地位。作者也坦承，关于公众态度的关键经验判断缺乏定论，只找到英国 CaSE 研究和另一篇论文作为暗示性支持。

「启示」 作者的核心结论是：为技术领域的艺术性辩护时，不能只诉诸艺术本身，而必须正面论证艺术如何让技术工作更有效；否则就等于让出了公众认为这项工作重要的主要理由。
